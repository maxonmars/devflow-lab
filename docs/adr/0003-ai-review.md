# 0003 — AI-ревью PR: `review <база>`, RAG в CI, комментарий в PR

Статус: принято по заданию дня 2.
Дата: 2026-10-13.

## Контекст

Задание дня 2 — автоматизация ревью кода: PR создан → diff → RAG по документации → LLM-ревью → комментарий в PR.
Ревью должно содержать потенциальные баги, архитектурные проблемы и рекомендации.

Каркас уже умеет RAG по документации проекта (ADR 0001) и git MCP-сервер с читающими инструментами (ADR 0002). Но
эмбеддинги идут только через локальную Ollama, а в раннере GitHub Actions её нет. git-сервер показывает diff только
рабочей копии и индекса, а не ветки относительно базы. Репозиторий `maxonmars/devflow-lab` публичный.

## Варианты

**Эмбеддинги в CI.**
- Ollama в раннере из Docker-образа: код эмбеддингов не меняется, цена — скачивание `bge-m3` (около 1,2 ГБ) и
  индексация на CPU. Кэш каталога моделей прироста не дал и не используется (см. демо).
- Облачный адаптер EmbeddingPort: новый секрет и новый адаптер; у DeepSeek API эмбеддингов нет.
- Self-hosted раннер с Ollama: отклонён — в публичном репозитории код чужого PR исполнялся бы на машине разработчика.

**Код в RAG.** Индексировать исходники в корпус или передавать код ревью напрямую. Корпус рассчитан на Markdown и
чанкинг по заголовкам; для ревью нужен именно изменённый код, а не похожий.

**Источник diff.** `git diff` прямо из host или инструменты git MCP-сервера. Host не запускает процессы git сам
(ADR 0002): песочница git собрана в сервере.

**Вывод.** Inline-комментарии к строкам, review с approve/request changes или один комментарий PR.

## Решение

- Новая команда `review <база>` (`app/review.ts`): её запускают и локально (`npm run dev -- review main`), и workflow.
  Модель вызывается один раз и без инструментов. Инструменты git-сервера host вызывает сам по фиксированному плану:
  - `git_changed_files { base }` — изменённые файлы относительно merge-base (`base...HEAD`);
  - `git_diff { base, path }` — diff одного файла относительно базы;
  - `read_file { path }` — содержимое отслеживаемого файла в HEAD; удалённые файлы попадают в контекст только diff'ом.
- Новые инструменты только читают и следуют прежней песочнице. Ref базы проверяется схемой (без `..`, `:`, пробелов и
  ведущего `-`) и `git rev-parse --verify`. `read_file` читает только HEAD и только отслеживаемые файлы.
- Документация приходит из RAG-индекса. Запрос — путь файла и начало его diff. Новая публичная функция rag
  `searchQueries` объединяет результаты по чанку с максимальным score, применяет порог `rag.similarityThreshold` и
  `rag.topK`. Если фрагментов нет, ревью строится без них.
- Новая фича `features/review`: сообщение для модели, промпт `prompts/review.md`, проверка трёх разделов ответа и
  итоговый Markdown. Фича не импортирует rag: документы получает простыми данными (`ReviewDoc[]`) от app.
- Лимиты — константы `app/review.ts`: не больше 20 файлов и 80 000 кодовых точек diff и содержимого. Пропущенное
  перечисляется в ревью.
- Настройка `review.outputFile`: Markdown ревью дополнительно пишется в файл атомарно.
- Workflow `.github/workflows/ai-review.yml` на `pull_request` (`opened`, `synchronize`, `reopened`):
  - Ollama из образа `ollama/ollama:0.34.4`, модель скачивается в каждом прогоне;
  - `rag index` в каждом прогоне, затем `review "origin/<base>"`;
  - один комментарий с маркером `<!-- ai-review -->`: обновляется на каждый push, иначе создаётся; тот же текст — в Job
    Summary;
  - DeepSeek с секретом `LAB_LLM_API_KEY`; job пропускается для PR из форков, при любой ошибке падает без комментария;
    required check не настраивается.

## Последствия

- Новые инструменты git-сервера автоматически видны модели и в `ask`/`info`: модель может читать файлы HEAD и
  сравнивать ветку с базой. ADR 0002 говорил, что о коде ассистент знает только список файлов и diff, — теперь есть и
  `read_file`.
- host разбирает текст `git_changed_files`, потому что `structuredContent` до host не доходит. Формат текста — контракт,
  закреплённый в README сервера и в тестах обеих сторон.
- Прогон в CI заметно дольше цели курса < 60 с: скачивание образа и модели, индексация на CPU раннера. Время
  фиксируется в демо и в этом задании не оптимизируется.
- Порог 0.55 калиброван на вопросах, а не на diff: запросы из diff могут дать пустой отбор. Это видно в разделе
  «Контекст ревью».
- PR из форков не ревьюятся: секреты им недоступны.
- Prompt injection через diff и содержимое файлов ограничен: у модели нет инструментов, вывод — только текст
  комментария. Событие `pull_request`, а не `pull_request_target`.
- Крупные PR ревьюятся частично. Стоимость прогона не измеряется: ModelPort не возвращает usage.

## Проверка

`npm run check`. В него входят:
- тесты git-сервера на настоящем git (база, изменённые файлы, `read_file`) и через `InMemoryTransport`;
- `searchQueries` с fake индексом;
- фича review с fake ModelPort;
- `review` в app с подменённой сессией;
- smoke собранного сервера с шестью инструментами.

Ручной прогон локально и на PR — [docs/demos/ai-review.md](../demos/ai-review.md).
