# 0004 — Ассистент поддержки: `support <тикет> <вопрос...>`, MCP-сервер тикетов, RAG по документации продукта

Статус: принято по заданию дня 3.
Дата: 2026-10-14.

## Контекст

Задание дня 3 — ассистент поддержки пользователей: мини-сервис отвечает клиенту на вопрос о продукте, опирается на RAG
по FAQ и документации и учитывает данные тикета и клиента, полученные через MCP из JSON-файла или CRM. Пример: «Почему
не работает авторизация?» — ответ зависит от того, как входит клиент и что с его аккаунтом.

Каркас уже умеет RAG по документации любого `project.root` (ADR 0001), MCP-сессии с читающими серверами (ADR 0002) и
host-driven сценарий «host вызывает инструменты сам, модель — один раз без инструментов» (`review`, ADR 0003). Продукта
с пользователями у devflow-lab нет.

## Варианты

**Кто загружает тикет.**
- Модель вызывает инструменты поддержки сама (как `info`): гибко, но ответ без тикета возможен, а данные клиента и
  выбор инструментов зависят от модели; нужен и поиск клиентов.
- Host вызывает `get_ticket` сам и передаёт текст модели (как `review`): тикет всегда в контексте, модель вызывается
  один раз без инструментов, поведение воспроизводимо.

**Источник данных.** Внешняя CRM — сеть, ключи и запись, что требует ADR песочницы и подтверждения человека. JSON-файл
внутри `project.root` — только чтение, без сети и секретов.

**Продукт.** Документация самого devflow-lab — вопросы клиентов к ней не подходят. Вымышленный продукт с отдельным
корпусом и индексом — корпус ассистента разработчика не меняется.

## Решение

- Демо-продукт «Acme Notes» — `examples/support-product/`: документация (корпус RAG), `support/tickets.json` с
  клиентами и тикетами и `support.config.yaml` (`project.root`, `rag.include`, индекс `.local/rag-support`). Запуск —
  существующим `--config-file`; шаблоны `rag.include` по умолчанию `examples/` не захватывают.
- MCP-сервер `servers/support` с одним читающим инструментом `get_ticket { id }`: тикет, клиент (тариф, статус
  аккаунта, способ входа, 2FA) и переписка. Сервер читает только файл из аргумента `--data`, на каждый вызов; ошибки —
  результат с `isError` и причиной.
- Настройка `support.dataFile` (по умолчанию `support/tickets.json`): путь внутри `project.root`, без `..` и абсолютных
  путей. Host передаёт серверу абсолютный путь.
- Команда `support <тикет> <вопрос...>` (`app/support.ts`): модель и индекс проверяются до запуска сервера; host
  вызывает `get_ticket` и передаёт текст модели целиком, не разбирая его; неизвестный тикет — ошибка без вызова модели.
  Сервер поддержки открывается только этой командой: в `ask`, `info` и `review` его нет.
- Документация — `searchQueries` по двум запросам: вопрос клиента и первые 1500 кодовых точек текста тикета; порог
  `rag.similarityThreshold`, `rag.topK`. Пустой отбор не отменяет вызов: ответ может опираться только на тикет.
- Новая фича `features/support`: сообщение, промпт `prompts/support.md` (без `app/system.md`, где роль — ассистент
  разработчика), три раздела «Ответ», «Источники», «Данные тикета», проверка разделов и номеров источников, итоговый
  Markdown. Фича не импортирует rag и mcp: документы и тикет приходят простыми данными.

## Последствия

- Данные клиента (имя, email, переписка) уходят провайдеру модели. Для вымышленных демо-данных это допустимо; для
  реальных нужны отдельное решение и маскирование.
- Prompt injection через текст тикета ограничен: у модели нет инструментов, вывод — только текст ответа.
- Rewrite запроса нет; порог 0.55 калиброван на вопросах разработчика, а не клиентов. Отбор виден в «Контексте ответа».
- Цитаты не проверяются, факты «Данных тикета» не сверяются с тикетом; нарушение формата отмечается, повтора нет.
- `support.config.yaml` задаёт пути относительно каталога запуска: команды запускаются из корня репозитория.
- Записи в JSON (смена статуса, ответ в тикет) нет: это потребовало бы отдельного ADR песочницы.

## Проверка

`npm run check`. В него входят:
- тесты сервера: схема и ошибки данных, формат тикета, протокол через `InMemoryTransport`;
- фича support с fake ModelPort;
- `support` в app с подменённой сессией и с настоящим сервером из host;
- smoke собранного сервера со списком инструментов `get_ticket`.

Ручной прогон — [docs/demos/support-assistant.md](../demos/support-assistant.md).
